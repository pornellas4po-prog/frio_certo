## Story

**Como** desenvolvedor,
**quero** confirmar no servidor uazapi do dono quais endpoints e headers valem,
**para** não construir em cima de documentação divergente.

## Acceptance Criteria

1. Testados no servidor do dono: criar instância, configurar webhook, gerar QR Code, ver status, enviar texto, desconectar e excluir.
2. Resultado registrado em `docs/Uazapi/contrato-validado.md` (endpoint, header, corpo e resposta de cada operação), resolvendo a tabela de divergências.
3. Nenhum token real gravado no repositório.

| Risco | Mitigação |
|---|---|
| Vazamento do token admin ou do token da instância | Tokens só em variável de ambiente local; respostas registradas com tokens mascarados; revisão do diff antes do commit |

## Dev Notes

**Origem:** PRD v0.3, História 1.7. Referências em `docs/Uazapi/` (5 arquivos, fornecidos pelo dono em 2026-11-15), que vêm de projetos anteriores e de versões diferentes da uazapi, por isso há divergências.

**Tabela de divergências (PRD v0.3):**

| Ponto | Opção A (uazapiGO v2 — `contrato-uazapi.md`, `configuracao-instancia-uazapi.md`) | Opção B (`instancia_uazapi.md`, `DICA_GEMS_GEMINI_UAZAPI.txt`) |
|---|---|---|
| Criar instância | `POST /instance/init` | `POST /instance/create` |
| Header de instância | `token` | `apikey` (legado v1) |
| Configurar webhook | **[a confirmar]** | `POST /webhook/set/{instance}` |
| Gerar QR Code | `POST /instance/connect` (corpo vazio) | `GET /instance/connect/{instance}` |
| Ver status | `GET /instance/status` | `GET /instance/connectionState/{instance}` |
| Enviar texto | `POST /send/text` | `POST /message/sendText/{instance}` |

**Já sabido pelas referências:**
- O header do token admin é `admintoken`, em minúsculas e **sem** "Bearer" (`configuracao-instancia-uazapi.md`).
- O token da instância é gerado na criação (`POST /instance/init`) e identifica a instância na rota do webhook `POST /webhook/{token}` (`contrato-uazapi.md`).
- O webhook precisa responder **200 OK imediatamente** (NFR11); isso será implementado na Story 2.4, não aqui.
- `contrato-uazapi.md` cita também `POST /send/media` para mídia; vale testar, porque a Story 2.5 vai precisar.

**Escopo:** spike de validação. **Não** criar código de produção em `backend/` ou `worker/`; as chamadas podem ser manuais (cliente HTTP ou curl). O resultado alimenta as Stories 2.1 a 2.5.

### Testing

Sem testes automatizados (spike). A evidência é o `contrato-validado.md`, com a resposta real de cada operação e os tokens mascarados.
